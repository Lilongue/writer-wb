# Технический долг и задачи по улучшению качества кода

Этот документ содержит список технических задач, направленных на улучшение архитектуры, читаемости и стабильности кода. Эти задачи не являются пользовательскими фичами, но важны для долгосрочного развития проекта.

---

|Задача|Проблема|Решение|
|:---|:---|:---|
|**Отсутствие тестов для `main` процесса**|После неудачных попыток исправить сломанный тестовый набор для `src/main/appLifecycle.test.ts`, было принято решение удалить его. В результате, ключевые модули в `src/main/` (сервисы, утилиты жизненного цикла и т.д.) остались без тестового покрытия. Исключение составляют утилиты в `src/main/services/utils/`, которые можно и нужно тестировать отдельно.|Восстановить тестовое покрытие для `main` процесса. Это потребует либо починки исходной проблемы с Jest (конфликт моков и состояний), либо полной переработки тестового окружения для `main` процесса с нуля с учетом необходимости изоляции тестов.|
|**Неэффективное обновление контента файла**|При изменении файла на диске, ассоциированного с текущим объектом (`details.path`), текущая логика в `useItemDetails` полностью перезапрашивает весь объект `details` (`get-item-details`), включая тяжелые данные из БД (например, связи). Это неэффективно и замедляет обновление UI.|**Рефакторинг**: Перенести ответственность за отслеживание `mtime` и обновление `content` файла непосредственно в компонент `FileContent.tsx`. `FileContent` будет получать `path` файла из `details`, а затем самостоятельно опрашивать файл через `PollingService`, читать его содержимое и управлять своим локальным состоянием `content` и `mtime`. Это разгрузит объект `details` и локализует ответственность за файловый контент.|
|**Сортировка настроек проекта**|Настройки проекта отсортированы в странном порядке, и разработчик не может легко изменить этот порядок.|Реализовать механизм, позволяющий разработчику задавать порядок следования настроек в интерфейсе.|
|**Тестирование бэкенда**|Отсутствуют юнит-тесты для ключевых бэкенд-сервисов (`ProjectService`, `NarrativeService`, `WorldObjectService`), что повышает риск регрессий.|Написать комплекты юнит-тестов для обеспечения стабильности и упрощения будущего рефакторинга.|
|**Рефакторинг хранения пользовательских полей (JSON -> Реляционная)**|Хранение определений полей и их значений в JSON-строках (согласно ADR-003) усложняет будущие операции, такие как удаление или переименование полей.|Провести рефакторинг хранения, перенеся данные в нормализованные реляционные таблицы (например, `template_fields` и `object_field_values`). Так как публичной версии не было, изменение можно внести напрямую в `schema.sql`.|
|**Рефакторинг `ImportExportService` для использования `system_name`**|Сервис импорта/экспорта использует `display_name` (`template.name`) для сопоставления шаблонов, что делает его хрупким при переименовании шаблонов пользователем. Это может привести к созданию дубликатов или пропуску объектов при импорте.|Переписать логику в `ImportExportService.ts`. Вместо `findTemplateByName` использовать новый, более надежный метод `findTemplateBySystemName`. Это потребует изменения методов экспорта (чтобы `system_name` включался в файл) и импорта (чтобы сопоставление шло по нему).|
