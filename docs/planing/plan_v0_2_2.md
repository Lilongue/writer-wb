# План работ для версии 0.2.2

Этот план включает в себя задачи, направленные на улучшение стабильности, пользовательского опыта и добавление полезных функций. Изначальный расчет был на 10 рабочих дней, однако по запросу пользователя объем был расширен.

## Утвержденные задачи

### Задача №1: Очищать область просмотра при удалении выбранного объекта

* **Проблема:** Если удалить объект, который в данный момент открыт в `ContentDisplay`, информация о нем не исчезает с экрана. `ContentDisplay` продолжает показывать устаревшие данные до тех пор, пока пользователь вручную не выберет другой объект или не снимет выделение.
* **Источник:** `docs/planing/tech_issues.md`
* **Аргументация:** Исправление этой ошибки немедленно улучшит качество и предсказуемость интерфейса. Низкий риск, высокая отдача для пользователя.
* **Оценка времени:** ~0.5 рабочего дня.

### Задача №2: Запретить создание объектов повествования с пустым именем

* **Проблема:** Приложение позволяет создавать объекты повествования с пустым именем. Это приводит к созданию файлов с некорректным именем и появлению "безымянных" элементов в дереве интерфейса, что сбивает пользователя с толку.
* **Источник:** `docs/planing/tech_issues.md`
* **Аргументация:** Важная валидация, которая предотвратит создание некорректных данных и улучшит стабильность работы приложения. Низкий риск, высокая отдача.
* **Оценка времени:** ~0.5 рабочего дня.

### Задача №3: Предоставлять обратную связь при попытке архивации используемого шаблона

* **Проблема:** При попытке заархивировать шаблон, который используется хотя бы одним объектом мира, операция молча не выполняется. Пользователь не получает никакого сообщения об ошибке или объяснения, почему архивация не произошла.
* **Источник:** `docs/planing/tech_issues.md`
* **Аргументация:** Значительно улучшит понятность работы приложения для пользователя. Он получит четкое уведомление о том, почему действие не может быть выполнено. Небольшая, но важная доработка для улучшения UX и предсказуемости системы.
* **Оценка времени:** ~0.5 рабочего дня.

### Задача №4: Внедрить тримминг (обрезку пробелов) для вводимых пользователем текстовых полей

* **Проблема:** Многие текстовые поля в приложении не обрезают начальные и конечные пробелы из вводимых строк. Это приводит к неаккуратному отображению имен и данных и может вызывать ошибки при поиске, сортировке или сравнении.
* **Источник:** `docs/planing/tech_issues.md`
* **Аргументация:** Это важная "гигиеническая" задача, которая повысит качество и консистентность данных в приложении. Она предотвращает множество потенциальных мелких ошибок и странного поведения в будущем.
* **Оценка времени:** ~1 рабочий день.

### Задача №5: Управление контентом для иерархических элементов

* **Проблема:** Родительские элементы повествования (например, "Часть" или "Глава") сейчас являются просто контейнерами и не могут иметь собственного контента, например, аннотации или общего описания.
* **Источник:** `docs/planing/features.md` (Модуль 3: Повествование)
* **Аргументация:** Добавление этой возможности сделает структуру повествования более гибкой. Пользователи смогут добавлять краткие описания для целых частей или глав, что полезно для планирования и навигации.
* **Оценка времени:** ~2 рабочих дня.
* **Примечание:** Требуется дополнительная проработка и уточнение требований, так как текущее описание может быть неточным.

### Задача №6: Использование ID для имен файлов повествования

* **Проблема:** Имена файлов для объектов повествования генерируются на основе их названий (`slugify(name)`). При переименовании объекта файл на диске не переименовывается, что создает рассинхронизацию. Это также может привести к коллизиям имен, если у объектов одинаковые названия.
* **Источник:** `docs/planing/tech_issues.md`
* **Аргументация:** Это ключевое улучшение для стабильности системы. Переход на использование `id.md` вместо `название.md` полностью отвяжет имя файла от названия объекта, устранит текущую рассинхронизацию и предотвратит возможные коллизии. Аналогичный механизм уже внедрен для "Объектов Мира", и этот шаг сделает поведение приложения консистентным.
* **Оценка времени:** ~2.5 рабочих дня.

### Задача №7: Архивирование / Экспорт проекта в zip

* **Проблема:** У пользователей нет простого способа создать полную резервную копию всего проекта (базы данных и всех файлов) одним действием.
* **Источник:** `docs/planing/features.md` (Модуль 2: Управление Проектом)
* **Аргументация:** Эта задача добавит важную утилитарную функцию, которая позволит пользователям легко создавать zip-архивы своих проектов. Это полезно как для резервного копирования, так и для переноса проекта. Так как это полностью новая, добавочная функция, она не несет рисков для обратной совместимости.
* **Оценка времени:** ~2 рабочих дня.
* **Примечание:** Требуется дополнительная проработка для определения того, *что*, *как* и *каким образом* экспортировать. Также необходимо учитывать будущую реализацию экспорта/импорта объектов мира, чтобы избежать создания двух механизмов для схожих задач. В идеале, эта задача должна быть синхронизирована с разработкой экспорта/импорта объектов мира, чтобы обеспечить консистентность решений.

### Задача №8: Экспорт объектов мира в отдельный файл (JSON или XML)

* **Проблема:** Отсутствует механизм для экспорта отдельных объектов мира или их наборов для обмена между проектами или архивации.
* **Источник:** `docs/planing/features.md` (Модуль 8: Импорт/Экспорт)
* **Аргументация:** Эта задача позволит пользователям экспортировать конкретные объекты мира (например, персонажей, локации) в машиночитаемый формат (JSON или XML). Это критически важный функционал для обмена данными между разными проектами WriterWorldBuilder, а также для создания пользовательских библиотек объектов.
* **Оценка времени:** ~3-4 рабочих дня.

### Задача №9: Импорт объектов мира из файла в текущий проект

* **Проблема:** Отсутствует механизм для импорта ранее экспортированных объектов мира в текущий проект.
* **Источник:** `docs/planing/features.md` (Модуль 8: Импорт/Экспорт)
* **Аргументация:** Импорт объектов мира является обратной стороной экспорта и не менее важен. Он позволит пользователям интегрировать объекты из других проектов или библиотек в свои текущие работы. Задача будет включать в себя разработку механизмов десериализации, создания новых объектов в базе данных и, что очень важно, решения возможных конфликтов (например, с уже существующими ID или именами) и корректного восстановления связей.
* **Оценка времени:** ~4-6 рабочих дней.

**Общее предполагаемое время выполнения плана: ~16-19 рабочих дней.**
