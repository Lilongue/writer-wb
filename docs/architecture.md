# Архитектура приложения

Этот документ описывает ключевые архитектурные решения и соглашения, принятые в проекте. Его цель — поддерживать консистентность кода при дальнейшей разработке.

---

## Структура Main-процесса (`src/main`)

Логика основного процесса разделена на несколько модулей для лучшей организации и разделения ответственности, следуя принципу Single Responsibility Principle.

### 1. Файлы в корне `src/main`

* `main.ts`: **Минимальная точка входа.** Единственная задача этого файла — импортировать и запустить `initializeApp` из `appLifecycle.ts`.
* `appLifecycle.ts`: **Оркестратор жизненного цикла.** Отвечает за управление событиями жизненного цикла приложения (`app.on('window-all-closed')`, `app.whenReady()`, `app.on('before-quit')`). Координирует инициализацию, вызывая `createWindow()` из `windowManager.ts` и `registerIpcHandlers()` из `ipcHandlers.ts`.
* `windowManager.ts`: **Менеджер окон.** Инкапсулирует всю логику, связанную с созданием и управлением окнами `BrowserWindow`.
* `ipcHandlers.ts`: **Центр обработки IPC.** Содержит регистрацию всех обработчиков `ipcMain.handle` и `ipcMain.on`. Этот модуль импортирует необходимые сервисы и делегирует им выполнение бизнес-логики в ответ на вызовы из `renderer`-процесса.
* `ipcUtils.ts`: **Вспомогательные утилиты IPC.** Содержит переиспользуемые функции, связанные с IPC, которые вынесены для предотвращения циклических зависимостей между другими модулями `main`-процесса (например, между `appLifecycle.ts` и `ipcHandlers.ts`).
* `services.ts`: **Инициализация сервисов.** Создает и экспортирует синглтон-экземпляры всех сервисов (`ProjectService`, `NarrativeService` и т.д.). Это позволяет другим модулям импортировать уже готовые экземпляры, а не создавать их.
* `menu.ts`: Отвечает за создание и управление нативным меню приложения.
* `preload.ts`: **Мост безопасности.** Скрипт, который выполняется в контексте `renderer`-процесса, но имеет доступ к API `Node.js`. Используется для безопасного предоставления `ipcRenderer` в React-приложение.
* `util.ts`: Общие утилитарные функции, не привязанные к конкретной бизнес-логике.

### 2. Сервисный слой (`src/main/services`)

Содержит классы, инкапсулирующие бизнес-логику приложения.

* `ProjectService.ts`: **Менеджер проектов.**
  * **Ответственность:** Управление жизненным циклом проекта: создание, открытие, закрытие. При создании проекта координирует работу других сервисов (`TemplateService`, `NarrativeService`, `ProjectSettingsService`) для инициализации базовой структуры и настроек. Включает метод `flushDatabase()` для принудительного сохранения всех отложенных изменений из WAL-файла в основной файл SQLite базы данных. Этот метод вызывается при закрытии проекта и перед архивацией для обеспечения целостности данных.
  * **Не должен:** Содержать логику, специфичную для доменных областей (повествование, мир и т.д.).

* `NarrativeService.ts`: **Менеджер повествования.**
  * **Ответственность:** Бизнес-логика, связанная с элементами повествования (части, главы, сцены). Реализует полный CRUD (создание, чтение, обновление метаданных, удаление) для этих элементов.
  * **Взаимодействие:** Использует `DAO` для получения и сохранения данных в БД. После изменения данных отправляет событие `narrative-changed` в `eventBus`.

* `ManuscriptService.ts`: **Сборщик рукописи.**
  * **Ответственность:** Сборка и экспорт иерархии повествования в различные форматы. На данный момент реализует экспорт в единый Markdown файл.
  * **Взаимодействие:** Использует `DAO` для получения полной структуры повествования. Не изменяет состояние приложения.

* `TemplateService.ts`: **Менеджер шаблонов.**
  * **Ответственность:** Бизнес-логика, связанная с управлением шаблонами (`narrative` и `world`). Реализует CRUD, архивацию, переименование, управление схемой полей, а также импорт предустановленных шаблонов из `assets/predefined-templates.json`.
  * **Взаимодействие:** Использует `GenericDao` для получения и сохранения данных в БД. После изменения данных, особенно схемы полей, отправляет событие `world-objects-changed` в `eventBus` для уведомления `renderer`-процесса.

* `WorldObjectService.ts`: **Менеджер объектов мира.**
  * **Ответственность:** Бизнес-логика, связанная с объектами мира (персонажи, локации). Реализует полный CRUD (создание, переименование, удаление) для этих объектов, а также управляет *значениями* их кастомных полей.
  * **Взаимодействие:** Использует `DAO` для получения и сохранения данных в БД. После изменения данных отправляет событие `world-objects-changed` в `eventBus`.

* `ProjectSettingsService.ts`: **Менеджер настроек проекта.**
  * **Ответственность:** Управление общими настройками проекта (например, имя автора, тема интерфейса). Предоставляет методы для получения и обновления настроек.
  * **Архитектурный паттерн:** Для настроек применяется паттерн разделения типа данных и их визуального представления. Поле `type` (`string`, `number`, `boolean`) отвечает за тип данных, в то время как опциональное поле `uiHint` (`readonly`, `file-path`, `textarea`) используется для выбора соответствующего UI-компонента в `renderer`-процессе.
  * **Взаимодействие:** Использует `DAO` для чтения и записи настроек в таблицу `project_settings`.

* `FileSystemService.ts`: **Менеджер файловой системы.**
  * **Ответственность:** Абстракция над модулем `fs`. Предоставляет методы для работы с файлами и папками, которые могут понадобиться другим сервисам.

* `ArchiveService.ts`: **Менеджер архивирования.**
  * **Ответственность:** Управление созданием ZIP-архивов проекта. Включает в себя сбор только необходимых файлов проекта (база данных, .wwb файл, директории narrative и world) и их упаковку.
  * **Обеспечение целостности данных:** Перед началом архивации вызывает `ProjectService.flushDatabase()` для принудительной синхронизации изменений из WAL-файла в основной файл базы данных, предотвращая потерю данных, которые могли быть не записаны на диск.
  * **Взаимодействие:** Использует `ProjectService` для получения информации о проекте и принудительного сохранения состояния БД, а также `FileSystemService` для работы с файловой системой. Использует стороннюю библиотеку `archiver` для создания ZIP-файлов.

* `ImportExportService.ts`: **Менеджер импорта/экспорта.**
  * **Ответственность:** Управление экспортом и импортом данных проекта. Реализует экспорт всех "Объектов мира" в единый JSON-файл, а также импорт объектов мира, шаблонов и связей из такого файла в текущий проект.
  * **Взаимодействие:** Использует `ProjectSettingsService` для получения имени проекта (используется для создания префиксов в именах шаблонов), `WorldObjectDao` для получения списка всех объектов и `TemplateDao` для получения определений их шаблонов. Для импорта объектов мира, шаблонов и связей использует `TemplateDao`, `WorldObjectDao` и `ConnectionDao` для создания соответствующих записей в базе данных, а также `MainNotificationService` для обратной связи пользователю.

* `MigrationService.ts`: **Менеджер миграций.**
  * **Ответственность:** Инкапсулирует логику обновления структуры проекта. Отвечает за сравнение версий, создание резервных копий БД, выполнение скриптов миграции из `src/main/migrations/` и обновление версии проекта в настройках.
  * **Взаимодействие:** Вызывается из `ipcHandlers` по запросу пользователя. Использует `ProjectService` для получения информации о текущем проекте.

### 2.1. Утилиты сервисов (`src/main/services/utils`)

Содержит сложные алгоритмы, вынесенные из сервисов для улучшения читаемости и тестируемости.

* `narrativeReorderer.ts`: **Алгоритм сортировки повествования.**
  * **Ответственность:** Инкапсулирует сложную логику определения нового родителя и порядка сортировки при drag-and-drop перемещении элементов в дереве повествования.
  * **"Контекстное Погружение" (Contextual Dive):** Реализует интеллектуальный алгоритм коррекции для невалидных перемещений. Вместо простой отмены действия, утилита ищет наиболее подходящее валидное место для вставки элемента, анализируя иерархию и "веса" шаблонов. Это позволяет обрабатывать как ошибки пользователя, так и причуды UI-библиотек, которые могут присылать некорректные данные о перемещении.
  * **Взаимодействие:** Используется исключительно `NarrativeService` для вычисления необходимых обновлений в БД.

### 3. Слой доступа к данным (`src/main/data/daos`)

Содержит классы, ответственные за прямое взаимодействие с базой данных.

* `BaseDao.ts`: **Базовый класс Data Access Object (DAO).**
  * **Ответственность:** Предоставляет базовую структуру для всех доменно-специфичных DAO, инкапсулируя механизм получения активного подключения к базе данных.
  * **Реализация:** Принимает в конструкторе функцию-поставщик (`() => better-sqlite3.Database`), которая предоставляет активное подключение к БД по требованию.

* `NarrativeDao.ts`: **DAO для сущностей повествования.**
  * **Ответственность:** Инкапсулирует SQL-запросы для CRUD-операций над элементами повествования (`narrative_items`).

* `WorldObjectDao.ts`: **DAO для сущностей объектов мира.**
  * **Ответственность:** Инкапсулирует SQL-запросы для CRUD-операций над объектами мира (`world_objects`) и их типами.

* `TemplateDao.ts`: **DAO для сущностей шаблонов.**
  * **Ответственность:** Инкапсулирует SQL-запросы для CRUD-операций над шаблонами сущностей (`entity_templates`).

* `ConnectionDao.ts`: **DAO для сущностей связей.**
  * **Ответственность:** Инкапсулирует SQL-запросы для работы со связями (`connections`) и глобальной таблицей сущностей (`all_entities`). Предоставляет методы для поиска `allEntityId` для конкретных сущностей и получения списка `allEntityId` всех объектов мира.

* `SettingsDao.ts`: **DAO для сущностей настроек проекта.**
  * **Ответственность:** Инкапсулирует SQL-запросы для CRUD-операций над настройками проекта (`project_settings`).

* **Общее для всех DAO:** Каждый доменно-специфичный DAO наследует (`extends`) `BaseDao`, что позволяет им использовать общее свойство для доступа к базе данных без дублирования кода. DAOs не должны содержать бизнес-логику, только выполнение запросов.

## Общие ресурсы (`src/common`)

* `types.ts`: **Общие типы данных.** Содержит интерфейсы и типы (`NarrativeItem`, `WorldObject` и т.д.), которые используются в нескольких частях приложения. Это обеспечивает единый источник правды для структур данных. Для обеспечения строгой типизации предустановленных шаблонов определены отдельные типы `PredefinedNarrativeTemplate` и `PredefinedWorldTemplate`.

* `utils.ts`, содержащий функцию `cleanNameInput`. Эта утилита отвечает за стандартизированную очистку пользовательских текстовых полей путем обрезки начальных/конечных пробелов и удаления неразрешенных символов. Интеграция этой функции происходит в коде процесса рендеринга (UI-слой), непосредственно перед вызовом IPC-методов для передачи данных в основной процесс. Таким образом, гарантируется, что данные уже очищены перед тем, как они отправляются в основной процесс для дальнейшей обработки и сохранения.

## Структура Renderer-процесса (`src/renderer`)

Архитектура `renderer`-процесса следует принципу **"Smart Hooks, Dumb Components"**. Сложные компоненты декомпозированы на три основных типа сущностей:

1. **Компонент-оркестратор:** Основной файл компонента (например, `WorldObjectTree.tsx`), который не содержит прямой логики данных или сложного состояния. Его задача — вызывать хуки и компоновать дочерние UI-компоненты.
2. **Кастомные хуки (Custom Hooks):** Файлы с префиксом `use...` (например, `useWorldObjectTreeData.ts`), которые инкапсулируют всю сложную логику: управление состоянием, взаимодействие с `ipcRenderer`, обработку событий и вычисления.
3. **UI-компоненты:** "Глупые" компоненты, отвечающие исключительно за отображение. Они получают все данные и колбэки через `props`.

### 1. Файлы в корне `src/renderer`

* `App.tsx`: Корневой компонент React. Управляет глобальным состоянием UI (например, какой элемент выбран) и компонует основные области макета (`Sider`, `Content`).
* `index.tsx`: Точка входа для React-приложения.

### 2. Контексты (`src/renderer/contexts`)

Содержит React Context'ы для управления глобальным состоянием, которое должно быть доступно множеству компонентов без "prop drilling".

* `ProjectContext.tsx`: Предоставляет состояние `isProjectOpen`, информирующее, открыт ли в данный момент проект. Управляет подписками на IPC-события `project-opened` и `project-closed` из `main`-процесса, а также проверяет начальное состояние проекта.

### 3. Компоненты (`src/renderer/components`)

Ключевые компоненты организованы в собственные директории, каждая из которых содержит компонент-оркестратор, хуки и дочерние UI-компоненты.

* **`WorldObjectTree/` и `NarrativeTree/`**:
  * **Оркестраторы:** `WorldObjectTree.tsx`, `NarrativeTree.tsx`.
  * **Хуки:** `useWorldObjectTreeData.ts`, `useNarrativeTreeData.ts` (управление деревом, IPC, контекстным меню, модальными окнами).
  * **UI-компоненты:** `WorldObjectModal.tsx`, `TreeContextMenu.tsx` и их аналоги для `NarrativeTree`.

* **`ContentDisplay/`**:
  * **Оркестратор:** `ContentDisplay.tsx`.
  * **Хуки:** `useItemDetails.ts` (загрузка данных, опрос ФС, управление связями) и `useItemEditor.ts` (управление состоянием редактирования, сохранение).
  * **UI-компоненты:** `ContentDisplayHeader.tsx`, `WorldObjectDetails.tsx`, `NarrativeDetails.tsx`, `FileContent.tsx`.
  * **Подсистема управления связями:**
    * **`ConnectionsManager.tsx`**: Компонент-менеджер, отвечающий за отображение списка связей. Он инкапсулирует всю логику фильтрации, включая управление состоянием фильтров и динамическое формирование UI на основе доступных данных.
    * **`ConnectionListItem.tsx`**: Новый "глупый" компонент, ответственный исключительно за рендеринг одного элемента в списке связей.
    * **`ConnectionGraph.tsx`**: Новый компонент, который визуализирует связи сущности в виде интерактивного графа, используя библиотеку `reactflow`. Он получает список связей и информацию о центральной сущности через `props` и отображает их как узлы и ребра, позволяя пользователю переключаться между текстовым списком и графическим представлением связей.

* **`TemplateManager/`**:
  * **Оркестратор:** `TemplateManagerModal.tsx` (управляет видимостью модальных окон, координацией импорта/экспорта шаблонов и объектов мира, а также обработкой данных перед передачей в `main`-процесс).
  * **Хуки:** `useTemplates.ts` (загрузка списка шаблонов, архивация).
  * **UI-компоненты:** `TemplateEditorModal.tsx` (инкапсулирует сложную форму редактирования шаблона). `ImportTemplatesModal.tsx` (модальное окно для импорта шаблонов и объектов мира из файла или библиотеки. Позволяет выбрать, какие элементы импортировать, и обрабатывает начальную десериализацию данных из файла, а затем передает их `main`-процессу для дальнейшей обработки).

* **`ProjectWizardModal.tsx`**:
  * **Оркестратор:** `ProjectWizardModal.tsx`.
  * **Назначение:** Реализует пошаговый "мастер" создания нового проекта. Отвечает за сбор данных от пользователя (имя проекта, расположение, структура повествования) и передачу их в `main`-процесс для создания проекта.

* **Простые компоненты:**
  * `ChecklistEditor.tsx`: Интерактивный компонент для управления чек-листом. Логика парсинга Markdown вынесена в `src/common/checklistUtils.ts`.
  * `AddConnectionModal.tsx`: Простой компонент-модал для добавления связей.

### 3. UI-компоненты и стилизация

* **Библиотека компонентов:** В качестве основной библиотеки UI-компонентов используется **Ant Design**. Это решение принято для ускорения разработки и получения консистентного, утилитарного интерфейса «из коробки».
* **Стилизация:** Глобальные стили и сбросы (`reset.css`) для Ant Design подключаются в `App.tsx`.

### 4. Система уведомлений

Для отображения пользователю уведомлений (об успехе, ошибках и т.д.) используется унифицированная система, взаимодействующая между `main`- и `renderer`-процессами.

* **`MainNotificationService.ts` (`src/main/services/NotificationService.ts`):** Новый централизованный сервис в `main`-процессе. Предоставляет методы (`error`, `warning`, `info`, `success`) для отправки уведомлений. Все уведомления отправляются в `renderer`-процесс через единый IPC-канал `show-notification` с типизированной структурой `{ type: NotificationType, title: string, content?: string }`. Это обеспечивает унифицированный механизм отправки уведомлений из любой части `main`-процесса.

* **`notificationService.ts` (`src/renderer/services/notificationService.ts`):** Централизованный сервис в `renderer`-процессе, предоставляющий методы для отображения различных типов уведомлений (`showError`, `showSuccess` и т.д.). Он обрабатывает входящие сообщения от `main`-процесса и вызывает соответствующий метод `Ant Design`.

* **Хуки `antd`**: Так как в `Ant Design v5+` статические вызовы `notification.error()` требуют глобального контекста, используется современный подход с хуками:

    1. В корневом компоненте `App.tsx` вызываются хуки `notification.useNotification()` и `message.useMessage()`.

    2. Эти хуки возвращают `api`-объект для вызова уведомлений и `contextHolder` для встраивания в дерево компонентов.

    3. `contextHolder`-ы рендерятся в `App.tsx`, обеспечивая работу системы.

    4. `api`-объекты сохраняются в экспортируемый `apiHolder` (`src/renderer/services/notificationService.ts`), делая их доступными для `notificationService`.

* **Типизация:** Для обеспечения типобезопасности и улучшения читаемости кода введен `enum NotificationType` в `src/common/types.ts`.

Этот подход обеспечивает гибкую, типобезопасную и расширяемую систему уведомлений, соответствующую требованиям `antd` и архитектуре Electron.

### 5. Система опроса файловой системы

Для централизованного управления периодическим опросом файловой системы (файлов и директорий) в `renderer`-процессе внедрен `PollingService`.

* **`PollingService.ts` (`src/renderer/services/PollingService.ts`):**
  * **Назначение:** Синглтон-сервис, который инкапсулирует логику управления таймерами `setInterval`/`clearInterval`. Он предоставляет унифицированный и безопасный механизм для запуска и остановки задач опроса.
  * **Механизм:** Управляет несколькими независимыми таймерами (например, для одного файла и одной директории) по уникальным идентификаторам. Методы `startFilePolling`, `stopFilePolling`, `startDirectoryPolling`, `stopDirectoryPolling` гарантируют, что для каждой задачи опроса активен только один таймер, предотвращая дублирование и "зомби-таймеры".
  * **Взаимодействие:** Используется кастомными хуками (`useItemDetails.ts`) и компонентами (`AttachedFiles.tsx`) для делегирования им ответственности за управление их индивидуальными задачами опроса файловой системы.

## Соглашения о файловой системе

Для связи сущностей приложения с файлами на диске используются соглашения о формировании путей.

* **Объекты мира (`world_objects`):
  * **Структура:** Для каждого объекта мира путь к его контенту формируется по правилу: `<корень_проекта>/world/<ID_шаблона>/<ID_объекта>/content.md`.
  * **Обоснование:** Используются неизменяемые идентификаторы (`template_id` и `object_id`) для формирования пути. Это гарантирует, что физическая связь с файлом `content.md` не нарушается при переименовании шаблона или самого объекта в интерфейсе пользователя, что решает проблему рассинхронизации и потери данных.

* **Объекты повествования (`narrative_items`):**
  * **Структура:** Все файлы, относящиеся к объектам повествования (частям, главам, сценам), хранятся в одной директории: `<корень_проекта>/narrative/`. Иерархия между элементами поддерживается исключительно в базе данных через `parent_id`.
  * **Именование файлов:** Имя файла генерируется единожды при создании элемента из его названия (например, `моя-сцена.md`) и сохраняется в базе данных.
  * **Проблема:** При переименовании элемента повествования в интерфейсе, соответствующий файл на диске **не переименовывается**. Это создает рассинхронизацию между названием элемента и именем файла. Хотя приложение продолжает работать корректно, ссылаясь на сохраненный в БД путь, это поведение неинтуитивно и является известной технической недоработкой (см. ADR-005).

## Взаимодействие процессов и событий

Для связи между `main` и `renderer` процессами, а также между модулями внутри каждого из них, используется комбинация из трех подходов.

### 1. Взаимодействие внутри Main-процесса: `eventBus`

* **Файл:** `src/main/eventBus.ts`
* **Технология:** `EventEmitter` из Node.js.
* **Назначение:** Обеспечивает слабую связанность (decoupling) между сервисами в `main`-процессе. Позволяет модулям публиковать события и другим модулям подписываться на них, не имея прямых зависимостей друг от друга. Это основной механизм для внутренней коммуникации и оповещения об изменениях состояния внутри `main`-процесса.
* **Примеры:**
  * `eventBus.emit('project-opened')` — отправляется `ProjectService` после успешного открытия проекта.
  * `eventBus.emit('project-closed')` — отправляется `ProjectService` при закрытии проекта.
  * `eventBus.emit('narrative-changed')` — отправляется `NarrativeService` после CRUD-операций или изменений в структуре повествования.
  * `eventBus.emit('world-objects-changed')` — отправляется `WorldObjectService` или `TemplateService` после изменения объектов мира.
  * `eventBus.emit('templates-changed')` — отправляется `TemplateService` после изменений в шаблонах.

### 2. Взаимодействие внутри Renderer-процесса: `appEventBus`

* **Файл:** `src/renderer/EventBus.ts`
* **Технология:** Пользовательская реализация `EventEmitter`.
* **Назначение:** Обеспечивает слабую связанность между компонентами React внутри `renderer`-процесса. Основное применение — отправка глобальных UI-событий, позволяющая избежать "пробрасывания" `props` (prop drilling).
* **Пример использования:**
  * При клике на пункт нативного меню `main`-процесс отправляет IPC-событие `top-menu-item-clicked`.
  * Корневой компонент `App.tsx` получает это событие и генерирует локальное событие `appEventBus.emit('top-menu-clicked')`.
  * Хуки `useNarrativeTreeData` и `useWorldObjectTreeData` подписаны на это событие и при его получении закрывают все открытые контекстные меню.

### 3. Межпроцессное взаимодействие (IPC)

* **`ipcHandlers.ts`** регистрирует слушателей для `eventBus` и пересылает их события в `renderer`-процесс с помощью `mainWindow.webContents.send('channel')`. Эта регистрация инициируется из `appLifecycle.ts` после готовности приложения.
* **`preload.ts`** действует как мост, безопасно предоставляя `renderer`-процессу доступ к определенным каналам `ipcRenderer`.
* **Renderer-процесс** (React-компоненты) использует `window.electron.ipcRenderer` для двух типов операций:
  * **Запрос-ответ:** `invoke('channel')` для получения данных от `main`-процесса (например, `project:create`, `get-narrative-items`, `dialog:show-open-dialog`).
  * **Подписка на события:** `on('channel', ...)` для реакции на события, инициированные `main`-процессом (например, `project-opened`).

  Список основных IPC-каналов, используемых для взаимодействия:

  | Канал IPC | Тип взаимодействия | Описание |
  | :------------------------------ | :---------------- | :------------------------------------ |
  | `project-opened` | `on` | **Источник:** `ProjectService` (main) после успешной загрузки проекта. **Назначение:** `ProjectContext` (renderer) переключает состояние `isProjectOpen` в `true`, активируя основной интерфейс. |
  | `project-closed` | `on` | **Источник:** `ProjectService` (main) при закрытии проекта. **Назначение:** `ProjectContext` (renderer) переключает `isProjectOpen` в `false`, возвращая приложение на экран приветствия. |
  | `open-in-external-editor` | `invoke` | **Источник:** `useItemDetails` (renderer) при клике на "Открыть в редакторе". **Назначение:** `ipcHandlers.ts` использует `shell.openPath` для открытия файла в системном приложении. |
  | `narrative-changed` | `on` | **Источник:** `NarrativeService` (main) после CRUD-операций. **Назначение:** `useNarrativeTreeData` (renderer) перезапрашивает дерево повествования для обновления UI. |
  | `export-full-manuscript` | `invoke` | **Источник:** `NarrativeTree` (renderer) из контекстного меню. **Назначение:** `ipcHandlers.ts` запускает `ManuscriptService` для сборки и сохранения файла рукописи. |
  | `top-menu-item-clicked` | `send` | **Источник:** `menu.ts` (main) при клике на любой пункт верхнего меню. **Назначение:** `App.tsx` (renderer) получает событие и через `appEventBus` генерирует локальное событие `top-menu-clicked` для закрытия контекстных меню. |
  | `world-objects-changed` | `on` | **Источник:** `WorldObjectService` или `TemplateService` (main) после изменений. **Назначение:** `useWorldObjectTreeData` и `useItemDetails` (renderer) перезапрашивают данные для обновления UI. |
  | `open-template-manager` | `on` | **Источник:** `menu.ts` (main) при выборе пункта в меню. **Назначение:** `App.tsx` (renderer) открывает модальное окно `TemplateManagerModal`. |
  | `open-project-settings` | `on` | **Источник:** `menu.ts` (main) при выборе пункта в меню. **Назначение:** `App.tsx` (renderer) открывает модальное окно `ProjectSettingsModal`. |
  | `show-notification` | `on` | **Источник:** Любой сервис в `main` через `MainNotificationService`. **Назначение:** `notificationService` (renderer) отображает уведомление через Ant Design. |
  | `open-project-wizard` | `on` | **Источник:** `menu.ts` (main) при выборе "Новый проект". **Назначение:** `App.tsx` (renderer) открывает `ProjectWizardModal`. |
  | `item-deleted` | `on` | **Источник:** `NarrativeService` или `WorldObjectService` (main) после удаления. **Назначение:** `App.tsx` (renderer) сбрасывает активный выбор, если удален текущий элемент, чтобы избежать показа устаревших данных. |

* **Скрипты миграций (`src/main/migrations/`):** Новая директория, предназначенная для хранения файлов с миграциями. Каждый файл должен соответствовать интерфейсу `Migration` и экспортироваться через центральный `index.ts` в этой же директории.
* **`ProjectService` (`src/main/services/ProjectService.ts`):** Модифицирован для интеграции с механизмом миграции. При открытии проекта он определяет, является ли версия проекта устаревшей. Если да, он информирует UI, который, в свою очередь, активирует возможность ручного запуска миграции.

**Процесс миграции:**

1. `ProjectService` при открытии проекта сравнивает версию проекта из БД с версией приложения.
2. Если проект устарел, через `eventBus` отправляется событие, которое активирует пункт меню "Обновить структуру проекта...".
3. Пользователь инициирует миграцию через меню.
4. Вызывается `MigrationService`, который:
    a. Создает резервную копию файла `project.sqlite`.
    b. Запраширует подтверждение у пользователя.
    c. Последовательно применяет все необходимые миграции из `src/main/migrations/`, оборачивая каждую в транзакцию.
    d. После успешного применения всех миграций обновляет версию проекта в БД до текущей версии приложения.
5. После завершения миграции проект автоматически перезагружается для обеспечения консистентности состояния приложения.
