# Технический долг и задачи по улучшению качества кода

Этот документ содержит список технических задач, направленных на улучшение архитектуры, читаемости и стабильности кода. Эти задачи не являются пользовательскими фичами, но важны для долгосрочного развития проекта.

---

## Список задач

1. **Использование перечислений (Enums):**
    * **Проблема:** В коде сервисов и IPC-обработчиков используются "магические строки" (например, `'narrative'`, `'world'`) для идентификации типов.
    * **Решение:** Провести рефакторинг, заменив строки на TypeScript Enums. Это повысит надежность, улучшит читаемость кода и автодополнение при разработке.

2. **Тестирование бэкенда:**
    * **Проблема:** Отсутствуют юнит-тесты для ключевых бэкенд-сервисов.
    * **Решение:** Написать комплекты юнит-тестов для `ProjectService`, `NarrativeService` и `WorldObjectService`. Это необходимо для обеспечения стабильности, предотвращения регрессий и упрощения будущего рефакторинга.

3. ✅ **Исправление адаптивности интерфейса:**
    * **Проблема:** В окне контента объекта кнопка может накладываться на текстовое поле при изменении разрешения окна.
    * **Решение:** Исправить верстку компонента для обеспечения корректного отображения элементов при любом разрешении.

4. ✅ **Унификация походов в базу:**
    * **Проблема:** Сейчас походы в базу сильно расползлись по сервисам из-за чего уже начинают дублироваться методы получения сущностей.
    * **Решение:** Ходить в базу через dao, как планировали изначально.

5. **Рефакторинг хранения пользовательских полей (JSON -> Реляционная модель):**
    * **Проблема:** Согласно `ADR-003`, определения полей (`fields_schema`) и их значения (`properties`) хранятся в виде JSON-строк в базе данных. Это решение, принятое для упрощения MVP, создает сложности для таких операций, как удаление, переименование и типизация полей. Текущая реализация добавления полей к шаблону решает основную проблему пользователя, но усугубляет этот технический долг.
    * **Решение:** В будущем провести рефакторинг хранения этих данных, перенеся их в нормализованные реляционные таблицы (например, `template_fields` и `object_field_values`).
    * **Примечание по миграции:** Так как публичной версии продукта еще не было, полноценный скрипт миграции существующих пользовательских данных не требуется. Изменение может быть внесено напрямую в схему `assets/database/schema.sql` и в код инициализации новой БД, что значительно упрощает будущий переход.
